# 我的身体单据（个人身体记录单据收纳与检索工具）

原生微信小程序。定位是**纯记录工具**：把要留存的纸质单据与电子凭证拍下来，按拍照日期归档，之后按日期 / 类型 / 关键词找回来。

**仅用于单据整理与检索，不提供任何专业意见；不收费，不做内容分析。**

## 快速上手（开源版）

1. 克隆本仓库，用**微信开发者工具**「导入项目」，目录选本仓库根目录（含 `app.json` / `project.config.json` 的那一层）。
2. `project.config.json` 里的 `appid` 是占位符 `touristappid`——导入时替换成**你自己的小程序 AppID**（或先用「测试号」体验）。
3. 无需 npm 构建、无需云服务、无需服务器域名：全部数据仅存于用户手机本地。
4. 离线回归测试：`node tools/tests/verify.js` 等全套用例见 `tools/tests/`；版本自检 `node tools/version.js verify`。
5. 想挂官方广告见 `config/ad.js`（默认关闭）；隐私指引填写对照 `docs/PRIVACY_GUIDE.md`。
6. 发布与版本管理约定见下文「版本管理」章节（`node tools/version.js release <tag> "说明"`）。

> 本仓库不含任何账号凭据 / 私钥 / 备案材料；`versions/` 快照与个人发布流程文档未随开源包分发。

## 当前版本边界（重要）

这一版是**单机版**：所有记录与照片只保存在用户手机微信的本地存储里，不上传服务器、没有账号体系、没有云服务依赖。

- 云服务开通确认在搭建时被取消，因此本版不含后端。工具本身功能完整，可直接使用。
- 好处：隐私最强、零后端成本、无需配置服务器域名。
- 代价：不能多设备同步、没有账号与找回能力。换手机、清除微信数据或卸载小程序**前必须自行导出备份**，否则数据不可恢复（见「备份与恢复」）。
- 若以后要做"家庭共享 / 自动同步 / 公开运营"，需要接入云端，见下方「接云端」。

### 类型名称与关键字

类型以固定分类 key 存储（`utils/type-store.js`），默认名称为：身体数据 / 我的清单 / 发票 / 检查报告 / 其他。用户可在「我的」页把每个名称改成任意文字（最多 8 字、不可重复），设置只存本机；改名不影响已有记录，也不影响按类型筛选。旧版记录里存的是中文标签，读取时会自动映射。

记录里的 `keyword` 是检索用关键字，可手动填写，也可由识别结果自动生成标签（空格分隔，最多 8 个）；旧版字段 `hospital` 在读取时兼容映射。首页搜索会命中其中任意一个词。

**标签 = 关键字的分词**（`utils/tag-kit.js`）：上传页「检索标签」面板和详情页编辑模式都常驻显示标签条，点标签文字或 `✎` 可**改字**、点 `×` 删除、点 `＋ 手动加标签` 自己写一个，改动立即同步回「关键字」输入框；反过来直接改输入框，标签条也实时跟着变。标签内部不允许空格（空格是分隔符），最长 12 字、最多 8 个、自动去重。所有入口都是普通视图 + `catchtap`，编辑框是页内输入框，不用 `button` 组件或 `editable` 弹窗（这两者在真机上出现过吞点击 / 不弹出）。删除按完整词匹配，不会误删长词里的子串。

### 一次上传多张照片（B13）

针对「一次拍/选好几张」的常见场景（同一张发票多页、或同时扫了发票和检查报告）：

- **自动编号**：一次选多张后，按选择顺序给每张照片编上「照片 1 / 照片 2 …」，缩略图角标显示编号，并提示「这份共 N 张」。之后再补选会接着往后编，不会重号。
- **逐张独立处理**：点哪张就进入「编辑中」，端侧识别、标签、备注都只作用于当前这张照片，互不影响。每张照片自己的识别结果、关键字标签、备注都单独存，不会串到别张。
- **删除即清空**：删除某张照片时，它的识别结果 / 标签 / 备注会一并删掉，不留孤儿数据；后面的照片编号自动顺延（照片 3 变照片 2）。
- **保存分组规则**：保存前页面会提示当前模式——若 N 张是同一类型，则**合并成一条记录**（每张照片作为一个 `items` 快照，含照片编号 / 标签 / 备注，记录的关键字是这些照片标签的并集，备注是拼接）；若 N 张分属不同类型，则**按类型自动拆成多条记录**，这些记录共用一个 `batchId` 批次号，便于「这一批原本是同一次上传的」回来找。两种模式都不需要用户手动拆，程序按类型分组后说明清楚再落盘。
- **存储结构**：记录的顶层仍兼容旧字段（`keyword` / `note` 为同组照片的并集 / 拼接），新增 `items: [{photoNo, tags, note}]` 与 `batchId`；旧记录没有 `items` 时详情页按空数组兼容展示。

### 保存后可单张补识别 / 改标签（B14，修 B13 反馈）

B13 把多张照片各自存好，但**保存后没法再单独处理某一张**——如果当时某张没点识别就保存了，事后回到记录里看不到、也改不了那张的标签和识别。B14 把这个口子补上：

- **详情页按张编辑**：在「单据」详情的「每张照片的标签与备注」区，每张照片都有「编辑这张 / 重新识别这张」两个按钮。
- **重新识别这张**：直接对已经落盘的那张照片再跑一次端侧识别，自动把新标签合并进这张（不丢原有的），点「保存这张」才生效；当前微信版本不支持端侧识别时会提示改用「手动加标签」。
- **单独改标签 / 备注**：可在该张内增删标签、改备注，和整条记录的编辑互不干扰；保存后整条记录的「关键字 / 备注」仍按各张并集自动刷新，首页检索不受影响。
- **上传页温和提示**：保存前若发现有照片还没识别，会在保存模式提示后追加一句「有 N 张还没识别文字，仍可保存；保存后到单据详情里可单独重新识别 / 编辑标签」，避免误以为必须当场识别完。
- **数据层放开**：`billStore.update` 原本只允许改 `visitDate/keyword/docType/note`，现在支持传入 `items`（按 `photoNo` 对应落盘照片，已做归一化与上限校验），单张补改能真正写回。

### 从备注提取标签（B15，修 B14 反馈）

用户反馈：某张照片识别不了（或没识别）时，只能把图里的文字手动复制到备注里，却**没有从这段文字自动出标签**的功能。B15 补上：

- **上传页「这张的备注」** 和 **详情页「编辑这张 → 这张的备注」** 下方各加一个「**从备注提取标签**」按钮。
- 点一下，本机规则（与端侧识别后的标签提取同源，`ocr.analyze`）把备注里的日期 / 标题 / 关键词整理成标签**追加**进这张的标签，不覆盖已有标签；空备注会提示，不会崩。
- 提取结果先落在本张的编辑态里，点「保存这张」（详情页）或随记录保存（上传页）才写回 `items`。
- 实现上统一用 `tagKit.words` 合并标签数组，避免 `tagKit.add` 吃掉空格把两个标签并成一个的坑（有回归用例覆盖）。

### 首页检索：日期与高频标签（B11）

**日期从文字搜索里拆出来了**。原来搜索框写「搜索关键字 / 类型 / 备注 / 日期」，日期混在全文匹配里既不好选也不好筛；现在文字搜索只查关键字 / 类型名 / 备注，日期由下面这张独立筛选卡负责：

- **专用组件**：微信原生 `<picker mode="date" fields="year|month|day">`。`fields` 是官方 `picker` 的内置属性（`year` = 只选年、`month` = 选到月、`day` = 选到某天），正好对应「年月日分段 / 某天」三种粒度。**不需要 npm、不需要第三方组件库、不需要服务器域名或联网**，隐私口径「所有数据仅保存在本机，不上传」不变。查过第三方方案：Vant Weapp 的 `van-datetime-picker` / `van-calendar` 要装 npm 包并在开发者工具里「构建 npm」，会多出依赖和体积；日历区间组件对「按某天找单据」也偏重，因此不引入。
- 先点「按年 / 按月 / 按天」切粒度，再点右侧虚线框打开官方滚轮选具体日期；选完显示中文条件（如 `2026 年 4 月 28 日`），可单独「清除」，也可「重置全部筛选」。
- **快捷日期段**（`utils/date-filter.js` 的 `quickBuckets`）：自动从已有记录里聚合出「有记录的年 / 月 / 日」，按记录条数从多到少排、同条数近的在前，点一下即筛选，不必开滚轮。手写日期 `2026-4-28`、`2026年4月28日`、`2026/4/28` 都会先归一化成 `YYYY-MM-DD` 再分段，与标准日期归入同一组；按段精确相等比较，`2026-01` 不会误命中 `2026-10`。
- 不同基础库对 `fields=year|month` 的 `event.detail.value` 返回格式不完全一致（`YYYY` / `YYYY-MM` / `YYYY-MM-DD` 都见过），`bucketFromPicker` 统一收敛，避免换机型后筛选失效。

**首页横向标签栏不再按固定类型顺序排**（截图里那排「全部 / 身体数据 / 我的清单 / …」也一直不能直接在首页编辑）。B11 起改为由 `utils/tag-store.js` 统计每条记录关键字分词后的**出现次数**，按频次从高到低展示，同频次按最近使用时间排，最多 12 个，每个标签带次数角标；B12 起可多选，默认「全部匹配」（AND，与 SO 多标签筛选一致），点右上可切「任一匹配」（OR），置顶标签排最前、忽略标签不显示，点「管理 ›」进标签管理页；点标签按完整词精确筛选，再点一次取消选中。标签数据只有一份（仍是 `keyword` 字符串），不额外存表，新增 / 编辑 / 删除记录后自动更新；没有对应记录的标签会自动从栏里消失并回到「全部」。类型筛选没丢，改成搜索栏右侧的原生 `picker`，「我的」页里的自定义类型名称功能照旧。

### 标签管理：参考 Stack Overflow（B12）

用户希望「标签页的管理和添加」参考 `stackoverflow.com`。查过官方帮助中心、标签词库页与官方博客后，借鉴了这四点，**全部在本机完成，不联网、不引入第三方组件**：

| SO 的做法 | 本项目的落地 |
|---|---|
| 输入 tags 时列出已有标签、**按频次排序**（官方博客 "ordered by frequency"），优先复用而不是制造同义词 | 上传页 / 详情页「＋ 手动加标签」输入框下方、标签管理页「新建标签」输入框下方，都实时显示按使用次数排序的已有标签；点一下填入，排除当前已用的标签与被忽略的标签 |
| `/tags` 标签词库页：搜索、按 popular / name / new 排序、显示每个标签的问题数 | 新增 `pages/tags/`：搜索框 +「按次数 / 按名称 / 按最近」排序 + 每个标签的条数与最近使用时间 |
| 重新打标签（re-tagging）与同义词合并 | **改名**（全局替换）、**合并**（把生僻标签并进已有标签，自动去重）、**删除**（只移除标签，记录与照片保留）；改动一次性写到所有相关记录 |
| 收藏（watched）/ 忽略（ignored）标签 | **置顶**（首页优先显示，带 ★）与 **忽略**（首页不出现、不进自动补全）；偏好存本机 `medical-bills.tagPrefs.v1` |

**添加标签**：在标签管理页输入新词 → 点「下一步」→ 勾选要加的记录 → 确认，批量加上；已含该标签的记录显示「已有」且不会重复添加。上传页与详情页原有的点标签改字 / × 删除 / ＋ 手动加标签全部保留，只是多了自动补全候选。

**数据一致性**：标签仍只是 `keyword` 字符串按空格分词，没有独立标签表；改名 / 合并 / 删除 / 批量添加通过 `billStore.applyKeywordPatches()` 一次读、一次写原子提交，避免中途失败留下半成品。`utils/tag-store.js` 里除偏好读写外都是纯函数，便于离线回归。顺带修掉一个 B10 遗留问题：`bill-store.js` 原来把 `keyword` 截到 40 字，第 4 个之后的标签会在保存时丢失，现已统一为与 `tag-kit.js` 一致的 80 字。**保存链路（拍照 → 识别 → 落盘 → 写记录）与识别逻辑一行未动。**

### 备份与恢复

单机版没有账号和服务器，因此备份走**用户自持文本**这条路：小程序不发起任何网络请求，也不上传服务器。

- **导出**：`utils/backup.js` 把 `medical-bills.records.v1` 里的记录、用户自定义类型名称、以及每张照片的 base64（`FileSystemManager.readFile({encoding:'base64'})`）序列化成一段 JSON 文本。可选「含照片（完整）」或「仅文字（体积小，恢复后照片看不到）」。
- **保管**：「复制备份内容」用 `wx.setClipboardData` 交给用户，自己粘贴到备忘录 / 文件传输助手 / 电脑；「导出为文件」用 `wx.shareFileMessage` 生成 `.txt` 由用户选择发给谁。后者在部分机型 / 类目会失败，页面会明确提示改用复制，**不把它当主路径**。
- **恢复**：粘贴到页内输入框，或用 `wx.chooseMessageFile` 从自己的微信聊天里选备份文件；先「检查备份内容」看记录数 / 照片数 / 备份时间，再经过**页内两步确认**（不用 `showModal`），最后选「合并」（按记录编号去重，默认）或「覆盖」（清掉现有全部记录）。
- **安全性**：照片先全部写进私有目录，**全部成功后才写记录**；任一步失败只删除本次新写的照片，已有记录与照片完全不动。校验覆盖 app 标识、版本号、记录结构、字段长度、记录数上限。
- **性能**：含照片的备份文本可达数 MB，因此完整文本只存在页面实例 `this._backupText` / `this._importText`，**绝不 `setData` 到渲染层**；页面只显示字数与统计，避免长文本把页面拖死。
- **隐私口径**：`setClipboardData` 是写入、`chooseMessageFile` 是用户主动选择、`shareFileMessage` 由用户点选接收方，本工具不自动读取剪贴板、不读取聊天记录、不保留备份副本。隐私页已同步说明。
- ⚠️ **2026-11-07 更正**：虽然语义上是"写入 / 主动选择"，但微信官方《用户隐私保护指引内容介绍》（2026-07-28 版）把 `wx.setClipboardData` 归入「读取你的剪切板」、`wx.chooseMessageFile` 归入「收集你选中的文件」、`wx.createVKSession` 归入「访问你的摄像头」。**官方按接口归类，不按语义直觉**。因此后台《用户隐私保护指引》须申报 **4 类**：选中的照片或视频信息、选中的文件、读取你的剪切板、访问你的摄像头；漏报的接口在真机会直接禁用（`errno 112`）。详见 `docs/PRIVACY_GUIDE.md`。

### 添加到桌面

「我的」页与备份页都有引导卡：安卓走右上角「···」→「添加到桌面」（部分机型需系统允许「创建桌面快捷方式」）；iPhone 不支持小程序加到主屏，改为「···」→「添加到我的小程序」，从微信首页下拉进入。页面明确写明**添加到桌面不等于备份**。

### 端侧文字识别

上传页「识别图中文字」用微信原生 VisionKit OCR（`wx.createVKSession` + `runOCR`，基础库 2.27.0+）：通过 `wx.createOffscreenCanvas` 把图片转成 RGBA 帧数据，在手机本机识别。照片与识别结果都不离开设备，不需要后端、密钥、服务器域名或第三方 SDK，因此**隐私口径不变** —— 后台简介「所有数据仅保存在本机，不上传」、隐私页、隐私指引（只申报 `Album`）均无需修改。

识别完成后会**自动提取标签**，按「日期 → 标题 → 关键时间 → 其他短词」的优先级排布，最多 8 个：

- 日期：完整年月日标准化为 `YYYY-MM-DD`；年份手写不全时不猜测。
- 标题：按单据抬头特征打分（如「告知书 / 须知 / 清单 / 回执 / 报告」），日期行、时刻行、称呼行会降权。
- 关键时间：`8:00`、`4月22日`、`1-3个月`、`提前三天`、`一个月` 等时刻 / 月日 / 时长 / 提前量，最多 4 个；房间号、电话号码不会被当成时间。

标签去重后自动写入「关键字」输入框供检索，可点 × 删除、点短文字行追加；图中日期另有「设为拍照日期」按钮，但**默认不改动拍照日期**（拍照日期指拍照当天，与图中日期未必相同）。提取只做文字切分与格式化，不做内容解读、语义分析、统计画像，不生成任何意见，识别结果也不上传。文字行仍可一键「填入备注」。

**识别质量闸门（B8）**：真机上曾出现端侧把整页文字挤成一行乱码（汉字夹数字 / 字母、半角杂乱符号），旧版会把乱码切碎成 3 个垃圾标签自动写进「关键字」，污染检索且要清理很麻烦。现在 `assessQuality()` 只做字形层面的噪声评分（整行超长、汉字夹字母、杂符号多、无可辨认汉字；若同时有可信日期与时间则降一档）。判定为乱码时：

- 保留原文供查看，但**不自动写关键字、不生成碎片标签、不猜标题**；仅严格正则命中的日期与时刻仍会保留；
- 页面明确提示「文字不清晰，未自动填写关键字。请手动点开上面的图片，然后两个手指分开长按识别，然后进入选词模式，选择「全选」和「复制」文字，填入下方「粘贴图中文字」框。」，并自动展开粘贴框（B9）；
- 用户**主动粘贴 / 输入的文字一律信任**（`analyze(texts, { trusted: true })`），照常提取日期 / 标题 / 关键时间，不受闸门影响；
- 超过 24 字的文字行不再被截断成 12 字垃圾标签，点它会提示直接输入简短的词；短文字行仍可手动加标签；
- 「填入备注」连点两次不会把同一段文字重复塞进备注。

B8 同时给详情页加了「**编辑这条记录**」：可改正关键字、拍照日期、类型与备注，一键清空备注，复用已有的 `billStore.update()`；保存失败有明确提示，照片路径不会被改动。这样识别不准留下的错字可以直接改，不必删掉重传照片。

**真机根因（B7 修复）**：这台设备上点自动识别后，倒计时停在 1 秒、保存与停止全部点不动 —— JS 主线程被冻住。此前 B5/B6 把帧从 1600 压到 512、加层层超时都没解决，因为 `runOCR` 是**同步推理**：所有 `setTimeout` 看门狗、倒计时、按钮点击排在同一条线程上，同步冻结时一起失效。

B7 修掉的是此前一直没动的地方：`updateAnchors` 的**原生回调栈里同步调用了 `session.off()` / `session.destroy()`**。客户端原生层正在分发回调时销毁会话，两侧互等形成死锁 —— 正好解释「结果回来了却收不了尾、整个页面失效」。现在 `finish()` 先 `resolve`，会话清理一律推迟到下一个宏任务。

其余加固：

- 输入帧最大边 512（约 1MB），`wx.compressImage` 异步缩小原图；解码、帧交付、会话启动、`runOCR` 之间让出宏任务；点击后延迟 800ms 启动；只跑一路，读图 4 秒 / 单路 3.5 秒 / 硬超时 9 秒。
- **结果直达**：`recognize(src, onTexts)` 在 `updateAnchors` 同一回调栈里同步调用 `onOcrResult()`，立刻复位识别状态、把文字行落到页面与 `medical-bills.ocr-last.v1`，标签整理放到下一个宏任务。即使后续同步推理占住线程，状态与文字也不丢。
- **卡住可恢复**：启动前写 `medical-bills.ocr-pending.v1`；用户退出重进时 `onShow` 检测到残留会收尾、清标记、引导到粘贴路径，且**不再自动重试端侧会话**；已暂存文字会自动恢复成标签。
- 「停止识别」调 `ocr.cancel()`；所有按钮为普通视图 + `catchtap`；看门狗超时不再用弹窗，只写页内提示与 toast；正则提取加 500 次循环上限。

**两条识别路径**：主路径是「识别图中文字（本机自动）」一键识别，普通用户直接点即可；若识别结果不清晰，用下方「粘贴图中文字」—— 操作步骤：点开上方单据照片 → 两个手指分开长按识别 → 进入选词模式 → 点「全选」和「复制」→ 粘贴到输入框。粘贴后走**同一套本地规则**自动出日期 / 标题 / 关键时间标签。输入框默认展开、支持 2000 字、实时暂存草稿（`medical-bills.manual-draft.v1`），退出重进可恢复；识别不清晰时也会自动展开。原文不上传、不存储，只有提取出的短标签写入记录。两种方式都不阻断归档与保存。

### 构建标记与环境自检

`utils/build.js` 的 `tag` / `time` 会在首页底部、我的页版本行、上传页底部显示构建号。**用于确认手机上跑的是哪一版代码** —— 应用卡改完代码不会自动同步，必须点「更新」重新发布，且微信里要彻底杀掉小程序再扫码重进（否则内存里仍是旧 JS）。

**版本管理（B11 起）**：`tools/version.js` 提供发布前自检、源码快照与一键回退，`versions/manifest.json` 记录版本历史，`versions/<版本号>/` 是可回退的源码副本。发布与排错流程见 `docs/RELEASE.md`。常用命令：

```bash
node tools/version.js status                   # 当前版本 / 包体积 / 快照数
node tools/version.js verify                   # 发布前自检（0 失败才能发）
node tools/version.js release B15 "改动说明"   # 统一版本行 + 自检 + 生成快照
node tools/version.js list                     # 版本历史与可回退快照
node tools/version.js rollback B11             # 回退（先自动备份当前代码）
```

`verify` 会检查 JS 语法、JSON、页面四件套、WXML 事件方法、红线词、三处版本行一致性、**上传代码包 < 2MB**、密钥与大资源误打包。`tools/` 与 `versions/` 已在 `project.config.json` 里排除，不进代码包；B10 及更早版本没有本地快照，要回到那些版本请用微信公众平台「版本管理」把已上传的开发版本重新设为体验版。

上传页底部还有一行实时环境信息（`构建 B13 · 保存可用 · 本机标签提取可用 · 基础库 x.y.z`），点「环境自检」可查看并复制：本机保存能力、识别方式、基础库版本、已选照片数、隐私同意状态、文字草稿、保存状态、上次保存点击时间、隐私待确认、拍照日期。保存能力显示「不可用」说明当前是网页预览而非微信，写不了本机文件。

### 保存兜底

`pages/upload/upload.js` 的保存流程不会静默失败：**「保存到本机」是吸底栏，滚动到页面任何位置都可见可点**，且用普通视图 + `catchtap` 实现（不依赖 button 组件的 disabled/loading 行为）。点下的第一瞬间就写一条吸底可见的步骤文字（`① 已收到点击 → ② 正在写照片 → ③ 写记录 → ④ 完成`），任何分支都不可能「完全没反应」。首次使用的隐私确认也移到吸底栏内，不再用弹窗拦住保存点击 —— 弹窗在个别机型/基础库上可能不弹出，正是 B4 真机上「按钮点了没反应」的最大嫌疑。

其余兜底：表单校验不通过会弹窗说明原因；失败弹窗显示完整原始错误；25 秒看门狗强制解锁；卡在「正在保存」超过 15 秒会自动恢复；切走再回来（`onShow`）也会解锁并收掉可能挂住的识别状态。保存成功会**弹出结果弹窗，明确显示保存目录与第一张照片的完整路径**，并在页面保留一张结果卡片（可复制路径、可直接跳「单据」页），不再用一闪而过的 toast 加自动跳页。识别等待期间吸底栏上方的识别提示每秒刷新「已等待 N 秒」，最多 12 秒自动结束。

`file-store.js` 的图片落盘按「saveFile 指定路径 → copyFile → saveFile 自动分配路径」三级兜底，压缩图失败改用原图重试，20 秒超时。照片只写入小程序私有目录 `wx.env.USER_DATA_PATH/bills/`，**不会出现在手机相册或文件管理器** —— 这一点必须在结果里讲清楚，否则用户会以为「点了没反应」。

## 接云端（以后要做时）

1. 开通云服务（登录 + 数据库 + 文件存储），拿到 `publicConfig`；
2. `utils/cloud.js` 用 `createMiniProgramWorkBuddyCloud({ endpoint, publishableKey, wx: createDiagnosticWx(wx) })` 初始化一次；
3. 建两张按 `owner_id TEXT DEFAULT auth.uid()` + RLS 隔离的表：`records`、`bills`；
4. 把 `utils/bill-store.js` 换成 `createTableAccess`，`utils/file-store.js` 换成 `cloud.storage.userPath` + `upload` / `createSignedUrl`；
5. 页面基本不用改；如需登录，加微信登录（`wx.login` → `signInWithWechat(code, appid)`）并在读写前做会话检查；
6. 更新隐私说明第三、四节，重新填写微信后台的用户隐私保护指引。
