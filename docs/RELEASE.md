# 版本管理与体验版发布 / 回退

适用工程：`medical-bills`（AppID `touristappid`）。
目标：**每次改动都有可回退的源码快照，每次发布前都能一键自检，不用靠记忆判断哪一版能发。**

---

## 1. 为什么要有这套东西

之前每轮改动都是直接覆盖工程文件，只在 `utils/build.js` 里留一个 `B10` 之类的标记。这样有两个问题：

- 一旦新版本有问题，没有旧代码可以退回，只能凭记忆把改动一点点撤销；
- 体验版「更新」失败时，无法快速判断是代码包问题、配置问题还是后台授权问题。

现在增加 `tools/version.js` + `versions/`：

| 路径 | 作用 |
|---|---|
| `tools/version.js` | 版本管理命令行（纯 Node 内置模块，无 npm 依赖） |
| `versions/manifest.json` | 版本历史、当前版本、快照索引 |
| `versions/<版本号>/` | 该版本的完整源码副本（目录形式，可直接用文本工具打开对比） |
| `versions/<版本号>/_snapshot.json` | 文件清单 + 每个文件的 sha256，用来核对回退是否完整 |
| `docs/RELEASE.md` | 本文件：流程与排错表 |

`tools/` 和 `versions/` 都已在 `project.config.json` 的 `packOptions.ignore` 里排除，**不会被打进小程序代码包**。

---

## 2. 命令速查

在工程根目录执行：

```bash
node tools/version.js status                  # 当前构建标记 / 包体积 / 快照数
node tools/version.js verify                  # 发布前自检（失败时退出码 1）
node tools/version.js list                    # 版本历史与可回退快照
node tools/version.js release B15 "改动说明"  # 统一版本标记 + 自检 + 生成快照（推荐）
node tools/version.js snapshot B15 "说明"     # 只存快照，不改版本号
node tools/version.js rollback B11            # 回退到某快照（先自动备份当前代码）
```

`verify` 会检查：所有 JS 语法、所有 JSON、页面四件套、tabBar 注册、WXML 事件方法是否都存在、医疗红线词、三处版本行是否与 `utils/build.js` 一致、打包排除规则、**上传代码包体积 < 2MB**、密钥与大资源是否误打进包。

## 3. 标准发布流程

1. 改代码。
2. `node tools/version.js verify` —— 必须 0 项失败。
3. `node tools/version.js release B15 "一句话说明"` —— 自动把 `utils/build.js`、首页 / 上传页 / 我的页的版本行统一成同一个版本号与时间，再自检一次，最后生成 `versions/B15/` 快照并写入 `manifest.json`。
4. **由你本人**打开应用卡 → 分享 → 体验版「更新」（这一步需要你的微信登录态，我不会索取 AppSecret、上传密钥或 token，也不能代点）。
5. 彻底杀掉微信进程再重扫二维码，确认首页底部显示 `构建 B15 · <时间>`；上传页底部环境行也是同一版本号。
6. 在 `versions/manifest.json` 里把该版本 `status` 从「已存快照」改成「体验版已发布」（可手工，也可下次发布时顺手改）。

> 小程序内的版本号（后台里的 1.0.x）由上传时填写，和这里的 `Bxx` 是两套编号：`Bxx` 用于手机上一眼确认跑的是哪份代码，1.0.x 用于微信后台版本管理。

---

## 4. 回退流程（两层保险）

### 本地源码回退

```bash
node tools/version.js list                    # 先确认目标版本有快照
node tools/version.js rollback B11
```

`rollback` 会：

1. 自动把**当前**代码存成 `pre-B11-<时间>` 快照（回退本身也可再撤销）；
2. 用目标快照覆盖源码文件，并写回版本历史；
3. 再跑一次 `verify`；
4. 只覆盖快照里有的文件，**不删除**后来新增的文件，避免误删（新页面若不再使用，从 `app.json` 的 `pages` 里去掉注册即可）。

回退后仍需你本人到应用卡分享面板点体验版「更新」，手机才会换版本。

### 微信后台回退（B10 及更早版本）

`B10` 及更早的版本**没有本地源码快照**（这套机制是 B11 才建的）。要回到这些版本，走微信公众平台：`管理 → 版本管理 → 开发版本 / 体验版本`，把之前上传过的那一版重新设为体验版。这一层是微信官方的版本回退，与本地快照互相独立。

## 5. 体验版发布失败排查表

> 说明：我看不到你手机 / 微信开发者工具上弹出的失败提示原文，下面第 1 项是**从工程侧确认存在、且这次已经修掉**的问题；其余是常见原因，需要你按提示文字对号入座。若修完仍失败，把失败提示截图或文字发我即可精确定位。

| # | 可能原因 | 怎么判断 / 怎么处理 |
|---|---|---|
| 1 | **代码包超过 2MB 主包上限**（本次最可能） | 修复前包内混进了 `base.png`(972 KB)、`assets/base.png`(972 KB)、`qrcode.png` 等与代码无关的图片，实测约 **2.2 MB > 2 MB**。`packOptions.ignore` 原先只排除了 `.workbuddy` / `docs` / `README.md`。现已补齐 `assets`、`tools`、`versions`、`base.png`、`qrcode.png`、`*.key`、`ICp.pdf`，`verify` 实测降到 **203.3 KB**。代码里没有任何地方引用这些图片，排除不影响功能 |
| 2 | **上传密钥 / 证书被打进代码包** | `docs/private.touristappid.key` 是小程序代码上传密钥，属于敏感文件。已随 `docs` 一并排除，`verify` 会额外扫描 `.key/.pem/.p12/.pfx` 并报错。密钥永远不要放进小程序代码包或提交到公开仓库 |
| 3 | 开发者工具未登录 / 登录态过期 / AppID 不匹配 | 工具右上角确认登录的是有该小程序权限的微信；`project.config.json` 的 `appid` 必须是 `touristappid` |
| 4 | 第三方平台授权过期或缺少「代码上传」权限集 | 在 mp 后台「设置 → 第三方设置」查看授权；授权变更后要重新触发上传 |
| 5 | 只上传了代码，没有设为体验版 | 上传成功后在「版本管理 → 开发版本」里点「选为体验版」；应用卡分享面板里的「更新」做的就是这一步 |
| 6 | 体验者名单 / 体验版二维码未刷新 | 确认微信号在「体验成员」里；更新后**彻底杀掉微信进程再重扫**，否则会命中本地旧缓存 |
| 7 | 代码本身有问题（语法、页面路径、JSON） | `node tools/version.js verify` 会覆盖这些，必须先 0 失败 |
| 8 | 类目 / 《用户隐私保护指引》 / 认证状态未通过 | 在 mp 后台看具体驳回提示；个人主体、认证年审、隐私指引补充说明都可能导致上传或设体验版被拦 |
| 9 | 使用 CI / miniprogram-ci 上传时密钥或 IP 白名单不对 | 检查密钥文件、IP 白名单与 `appid`；本工程默认走开发者工具 / 应用卡，不用 CI |

### 发布前 10 秒自查

```bash
node tools/version.js status && node tools/version.js verify
```

看到「0 项失败 + 上传代码包约 2xx KB」就可以去点体验版「更新」。

## 7. 边界与约定

- 工具只在本地读写文件，**不会**调用微信上传接口、不会代发体验版、不会索取或保存 AppSecret / 上传密钥 / token。
- 快照只包含发布用源码（`app.*`、`sitemap.json`、`project.config.json`、`pages/`、`utils/`、`config/`），不含 `docs/`、图片、密钥、README 与版本目录本身。
- 每次 `release` / `rollback` 都会写 `versions/manifest.json`，这个文件应随工程一起保留，不要删除 `versions/` 目录。
- `.workbuddy/` 是项目数据目录，不进版本快照、不进代码包，也不要删除。
